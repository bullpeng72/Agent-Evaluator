# 서문: AI 에이전트 평가, 왜 지금인가


## 이 책이 필요한 이유

소프트웨어 세계는 지금 조용하고도 근본적인 전환점을 맞이하고 있습니다. 기존 소프트웨어는 결정론적입니다. 함수에 동일한 입력을 넣으면 항상 동일한 출력이 나옵니다. 테스트도 그 원칙 위에 세워졌습니다. `assert result == expected` 한 줄이면 충분했습니다.

AI 에이전트는 다릅니다. 에이전트는 도구를 선택하고, 외부 API를 호출하고, 여러 단계에 걸쳐 스스로 계획을 수정합니다. 같은 질문에도 매번 다른 경로로 답에 도달합니다. 때로는 환각(hallucination)으로 틀린 정보를 자신감 있게 전달하고, 때로는 허가되지 않은 도구를 실행하거나 민감한 데이터를 출력에 포함시키기도 합니다. `assert`는 이 복잡성을 포착하지 못합니다.

이 책은 그 간극을 메우기 위해 쓰였습니다. AI 에이전트를 프로덕션에 배포하기 전에 **무엇을**, **어떻게** 평가해야 하는지를 실무 중심으로 다룹니다. 이론보다 코드, 개념보다 실제 동작하는 예시를 우선합니다.

특히 이 책은 **AI Native** 관점에서 평가를 다룹니다. AI를 기존 프로세스에 추가하는 AI First와 달리, AI Native는 AI를 프로세스의 핵심 실행 주체로 설계합니다. AI Native 환경에서 에이전트는 단순한 도구가 아닌 자율적 판단자입니다. 정답이 명확하지 않은 태스크를 수행하고, 여러 에이전트가 상호작용하면 설계 시점에 예측할 수 없는 행동이 나타납니다. `assert result == expected`는 이 복잡성을 포착할 수 없습니다. **단순히 "잘 동작하는가"를 측정하는 것을 넘어, "배포해도 되는가"를 판정하는** 새로운 평가 패러다임이 필요합니다.

## Harness Engineering이란

이 책은 **Harness Engineering**이라는 관점으로 AI 에이전트 평가를 다룹니다.

기존 소프트웨어 테스팅은 "버그가 없는가"를 묻습니다. Harness Engineering은 다른 질문을 던집니다. **"이 에이전트는 배포해도 되는가?"** 그 질문에 답하기 위해 배포 기준을 문서나 관행 대신 코드로 선언합니다.

```python
# Harness Engineering의 핵심 패턴 — Config-as-Code
from agent_evaluator import QuickEval

eval_q = QuickEval("results/")

# ① Tracker — @eval_q.qa 데코레이터가 실행 중 latency·token·accuracy를 자동 기록
@eval_q.qa
def my_agent(question, ground_truth=""):
    return llm.invoke(question)  # 실제 LLM 호출 (OpenAI·Anthropic 등)

# ② Config  — 배포 기준을 코드로 선언 (tcr=85, accuracy=70)
# ③ Gate    — 기준 위반 시 exit 1로 CI/CD 파이프라인을 자동 차단
eval_q.gate(tcr=85, accuracy=70)
```

이 패턴은 세 가지 역할로 구성됩니다.

- **① Tracker** — `@eval_q.qa` 데코레이터가 에이전트 실행 중 지표를 자동으로 관찰하고 기록합니다. 함수 호출 한 번으로 latency, token 사용량, task completion 여부가 측정됩니다. "무엇이 실제로 일어났는가"에 대한 답입니다.
- **② Config** — `tcr=85, accuracy=70` — "이 에이전트는 어떤 조건을 만족해야 배포될 수 있는가"를 코드로 선언합니다. 숫자 두 개가 품질 계약서 역할을 합니다. 문서나 관행 대신 코드로 고정하기 때문에 LLM 모델이 바뀌어도, 팀원이 바뀌어도 기준이 흔들리지 않습니다.
- **③ Gate** — `eval_q.gate(...)` 호출이 Config 위반 여부를 종합 판정합니다. `HarnessEvaluationGate`가 7개 Gate를 한 번에 평가해 기준을 충족하면 `exit 0`, 위반하면 `exit 1`을 반환합니다.

이 세 역할이 결합하면 배포 기준이 **실행 가능한 코드**가 됩니다. 코드로 고정된 기준은 LLM 모델이 바뀌어도, 프롬프트가 수정되어도 흔들리지 않습니다.

여기서 중요한 구분이 생깁니다. **"Agent = Model + Harness"** — 모델은 에이전트의 *능력*을 담당하고, Harness는 그 능력이 프로덕션 기준을 실제로 충족했는지를 판정합니다. "잘 동작한다"는 것과 "배포해도 된다"는 것은 다른 판단입니다. 전자는 모델의 영역이고, 후자는 Harness의 영역입니다.

## 지표를 이해하는 두 가지 관점

Harness Engineering의 58개 지표는 **두 가지 관점**에서 바라볼 수 있다. 어느 쪽이 맞고 틀리냐의 문제가 아니라, **독자의 역할**에 따라 진입점이 다르다는 의미다.

### 관점 1 — Gate A–G (품질 차원별 분류)

"에이전트가 목표를 달성했는가? 보안 경계를 지켰는가? 배포해도 되는가?"

7개 Gate는 **품질 관리자·의사결정자**가 에이전트를 평가하는 방식이다. 각 Gate는 하나의 품질 차원을 대표하며, 통과/경고/실패 세 가지 판정으로 배포 가능 여부를 명확히 제시한다.

```
Gate A — 목표달성   Gate B — 행동무결성   Gate C — 신뢰성
Gate D — 성능계약   Gate E — 보안경계     Gate F — 다중에이전트
Gate G — 운영관측성
→ "어떤 차원에서 문제가 있는가?" 를 한눈에 파악
```

### 관점 2 — Tracker + Config (구현 단위별 분류)

"어떻게 측정할 것인가? 어떤 기준을 코드로 선언할 것인가?"

25개 Tracker와 33개 Harness Config는 **개발자**가 평가를 구현하는 방식이다. Tracker는 자동으로 데이터를 수집하고, Config는 데코레이터에 선언하는 기준서다.

```python
# 개발자 관점: Tracker(자동 측정) + Config(기준 선언)
eval_q = QuickEval("results/")

@eval_q.qa
def my_agent(question, ground_truth=""): ...
# → Tracker가 자동으로 accuracy, latency, tool_calls 등을 기록

# Config-as-Code: 배포 기준 선언 (위반 시 exit 1)
eval_q.gate(
    tcr=85, accuracy=70,                # Gate A — accuracy ≥ 70%, TCR ≥ 85%
    latency_p95=2.0,                    # Gate D — p95 응답속도 ≤ 2.0s
    tool_f1_min=0.8,                    # Gate B — 도구 선택 정확도 ≥ 0.8 (F1)
)
```

### 두 관점의 연결고리

두 관점은 **같은 데이터를 서로 다른 언어로 설명**한다.

| 개발자가 선언하는 것 | QA 관리자가 보는 것 |
|-------------------|--------------------|
| `eval_q.gate(accuracy=70)` + Tracker가 기록한 `accuracy` | Gate A — 목표달성 점수 |
| `eval_q.gate(latency_p95=2.0)` + Tracker가 기록한 `latency` | Gate D — 성능계약 점수 |
| `eval_q.gate(tool_f1_min=0.8)` + Tracker가 기록한 `tool_calls` | Gate B — 행동무결성 점수 |

**개발자**는 `eval`(QuickEval Tracker)과 `eval_q.gate(accuracy=70, latency_p95=2.0, tool_f1_min=0.8)`(Config)를 통해 "어떤 데이터를 어떤 기준으로 측정할지" 선언한다.  
**QA 관리자**는 Gate A–G를 통해 "어떤 차원에서 배포 가능한지" 판단한다.  
같은 시스템, 두 가지 언어 — 이 책의 Part II는 그 둘을 동시에 설명한다.

> **읽기 전략**: Gate A–G 관점이 먼저 필요하다면 Part II의 각 챕터를 개요와 Config 설정 섹션 중심으로 읽는다. Tracker 구현이 필요하다면 Tracker 상세와 코드 예제 섹션을 깊이 읽는다.

## 이 책이 다르게 생각하는 것들

이 책은 AI 에이전트 평가에 대해 몇 가지 전제를 가지고 있습니다. 기존 소프트웨어 테스팅 관점과 다르게 생각하는 부분입니다.

**1. 품질은 숫자 하나가 아니라 분포다**

`eval_q.gate(accuracy=70)`은 정확도 70% 이상을 배포 기준으로 선언합니다. 하지만 Tracker가 집계한 `accuracy = 85`(%)라는 단일 수치는 완전한 정보가 아닙니다. 같은 85%라도 분산이 작으면 안정적인 에이전트, 분산이 크면 예측 불가능한 에이전트입니다. 배포 판정에는 단일 수치가 아니라 통계적 신뢰 구간이 필요합니다. 이 책은 Wilson Score Interval(성공률의 신뢰 하한을 구하는 통계 기법)같은 확률론적 임계값 설정을 다룹니다.

**2. AI는 AI가 가장 잘 평가한다 — 단, 구조적 제어 아래에서**

사람이 수백 개의 에이전트 응답을 읽으며 품질을 채점하는 것은 현실적이지 않습니다. LLM Judge는 선택 사항이 아니라 Harness Engineering의 핵심 부품입니다. 다만 "AI가 AI를 평가한다"는 구조에는 순환 참조의 위험이 있습니다. 평가 모델 자체가 편향되거나 오작동할 수 있기 때문입니다. 이 책은 LLM Judge를 알고리즘 기반 Tracker와 병행해 사용하는 방법, 그리고 `sample_rate`로 LLM Judge 비중을 제어하는 방법을 다룹니다.

**3. 배포 전 테스트만으로는 충분하지 않다**

에이전트가 사용하는 LLM 모델이 업데이트될 수 있습니다. 프롬프트가 바뀔 수 있습니다. 외부 데이터가 변할 수 있습니다. 이 책은 코드·모델·프롬프트·데이터, 4가지 변경 소스를 기준으로 드리프트를 감지하고 Harness를 재보정하는 방법을 다룹니다.

**4. 돌발 행동은 탐지 목록 밖에서 온다**

SQL Injection 패턴 목록이 아무리 방대해도, 목록에 없는 공격은 통과합니다. 의미 기반 탐지가 패턴 매칭과 반드시 함께해야 합니다. 이 책은 보안 경계(Gate E)에서 2계층 탐지를 다룹니다.

**5. 평가는 배포 전에 끝나지 않는다**

프로덕션 에이전트의 평가는 배포 후에도 계속됩니다. `agent-eval trend`로 순차 실행 결과를 추적하고, `RunTrendAnalyzer`로 회귀를 조기 감지하며, 평가 결과를 프롬프트 개선에 환류하는 자기개선 루프가 완전한 Harness Engineering입니다.

## Agent-Evaluator SDK 소개

이 책에서 사용하는 **Agent-Evaluator**는 AI 에이전트 Harness Engineering을 위해 설계된 오픈소스 Python SDK입니다.

- **버전**: v0.9.7 (Beta)
- **라이선스**: MIT
- **지원 Python**: 3.8 ~ 3.13

핵심 설계 원칙은 세 가지입니다. 첫째, **외부 의존성 없는 네이티브 평가**입니다. 58개 지표 중 대부분은 OpenAI나 Anthropic API 없이 로컬에서 즉시 계산됩니다. 둘째, **데코레이터 한 줄**로 평가를 시작할 수 있는 최소 마찰 설계입니다. 셋째, **Config-as-Code 패턴**으로 배포 기준을 코드로 선언하고 Gate로 자동 판정합니다.

58개 지표는 7개의 배포 판정 차원(**Gate A–G**)으로 구성됩니다. 각 Gate는 독립적인 Harness Config(기준 선언)와 Tracker(실측)를 가집니다. `agent-eval gate` CLI 또는 `eval_q.gate()` 호출이 7개 Gate를 종합해 최종 배포 판정을 내립니다 — 기준을 충족하면 `exit 0`, 위반하면 `exit 1`로 CI/CD 파이프라인을 자동 차단합니다.

| Gate | 품질 차원 | 구성 | 평가 질문 |
|------|-----------|------|-----------|
| Gate A | 목표달성 | Tracker 3종 + Config 6종 | 에이전트가 지시를 완수했는가? |
| Gate B | 행동무결성 | Tracker 2종 + Config 6종 | 의도치 않은 행동이 없었는가? |
| Gate C | 신뢰성 | Tracker 2종 + Config 5종 | 일관되고 재현 가능한가? |
| Gate D | 성능계약 | Tracker 2종 + Config 5종 | SLA/비용 계약을 지켰는가? |
| Gate E | 보안경계 | Tracker 5종 + Config 3종 | 공격·유출을 차단했는가? |
| Gate F | 다중에이전트 | Tracker 2종 + Config 4종 | 교착 없이 협력했는가? |
| Gate G | 운영관측성 | Tracker 0종 + Config 4종 | 실패 원인을 즉시 추적할 수 있는가? |

> Harness Gate 직접 매핑 Tracker 16종 + Config 33종 = 49개, 
> 운영 지원 Tracker 9종(ConversationSession · Feedback · Anomaly · Cost · Streaming 등) 포함 시 
> **Native Tracker 25종 + Harness Config 33종 = 58개 지표**

## 실습 환경 안내

이 책의 모든 코드 예시는 **Python 3.8 이상** 환경에서 실행됩니다. 실습을 위해 다음 환경이 필요합니다.

```bash
# 기본 설치 — 코어 지표 + LLMJudge 엔진
pip install agent-evaluator

# 권장 설치 — 대시보드 · OTEL 모니터링 · PDF 포함
pip install "agent-evaluator[sdk]"

# 이 책의 모든 예제 실행
pip install "agent-evaluator[examples]"

# 설치 확인
agent-eval --version
# → agent-evaluator 0.9.2
```

LLM API를 사용하는 예시에서는 OpenAI 또는 Anthropic API 키가 필요합니다. `agent-eval init`을 실행하면 대화형 마법사가 키를 안내하고 `.env` 파일에 자동으로 저장합니다.

```bash
agent-eval init
```

AI 에이전트는 더 이상 실험실의 프로토타입이 아닙니다. 지금 이 순간에도 수많은 서비스의 핵심 로직을 담당하고 있습니다. 배포 기준 없이 배포된 에이전트는 언제 어떤 방식으로 실패할지 알 수 없습니다.

AI Native 환경에서 이 불확실성은 구조적입니다. 비결정론적 동작, 정답의 부재, 돌발 행동 — 이것들은 더 나은 프롬프트로 해결되지 않습니다. 검증 구조 자체가 필요합니다. Harness Engineering은 그 불확실성을 측정 가능하고, 코드로 선언 가능하고, 자동으로 판정 가능한 것으로 바꿉니다.

이 책이 그 전환에 도움이 되기를 바랍니다.
