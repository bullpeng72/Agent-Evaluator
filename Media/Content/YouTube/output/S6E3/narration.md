## [MAIN1] 이식의 제1원칙 — 아무것도 깨지 않는다

[SLIDE: 제1원칙 — 측정과 수정은 절대 동시에 하지 않는다]

자, 경험 있으신 분들은 공감하실 거예요. 기존 프로젝트에 뭔가 새 기능을 붙이려고 코드를 열었다가, "어, 이 부분 리팩터링하면 딱 좋겠는데?" 하면서 원래 목적이 사라진 경험, 한 번쯤은 있으시죠?

평가 코드 이식할 때 이게 제일 흔한 실수입니다. 측정 코드 삽입하면서 함수 인터페이스도 살짝 바꾸고, 로그 남기려다 기존 흐름에 분기도 추가하고, 하는 김에 파라미터 정리도 하고. 얼핏 보면 효율적인 것 같죠? 근데 이게 함정이에요.

측정과 수정을 동시에 하면 나중에 버그가 났을 때 어디서 문제가 생겼는지 구분이 안 돼요. "평가 코드 때문이야, 리팩터링 때문이야?" 디버깅이 두 배로 힘들어집니다. 그리고 최악의 경우, 측정이 오히려 시스템을 불안정하게 만들어요.

1단계의 원칙은 딱 하나입니다. **기존 코드의 입력과 출력을 바꾸지 않는다. 반환값만 관찰한다.** 이걸 "레벨 0 침습"이라고 부릅니다. 함수가 뭘 반환하는지만 보고, 내부는 절대 건드리지 않는 거예요.

이 원칙 위에서 오늘 사용할 도구들을 빠르게 정리해볼게요. 처음 보시는 분들을 위해 세 가지만 기억하시면 됩니다.

첫 번째, `QuickEval`입니다. 평가 세션을 가장 간단하게 시작하는 파사드예요. `QuickEval("results/")` — 이 한 줄이 평가 세션 전체를 열어줍니다. 내부적으로 `PerformanceMonitor`와 `EvalDecorator`를 다 챙겨주기 때문에 여러분이 직접 설정할 게 거의 없어요.

두 번째, `@eval_session.qa`입니다. 에이전트 함수에 붙이는 데코레이터예요. 이 데코레이터가 붙은 함수를 호출할 때마다 자동으로 TaskResult가 생성되고, monitor에 기록됩니다. 조건이 하나 있어요 — 함수가 `str`을 반환해야 한다는 것. 이게 왜 중요한지는 QAAgent 이식 부분에서 자세히 설명드릴게요.

세 번째, `create_taskresult()`입니다. 데코레이터 적용이 불가능한 상황 — 예를 들어 반환값이 Pydantic 모델이거나, 클래스 메서드라서 데코레이터 위치가 애매한 경우 — 에 수동으로 결과 한 건을 기록하는 헬퍼 함수예요. 이건 ContentWriter 이식할 때 쓰게 됩니다.

정리하자면, `str` 반환하는 함수엔 `@eval_session.qa` 바로 붙이면 되고, 그게 안 되면 `create_taskresult()`로 우회합니다. 이 두 패턴만 알면 오늘 실습 전부 커버됩니다.

## [MAIN2] 침습도 레벨 — 얼마나 건드릴 것인가

[SLIDE: 침습도 0~3 — 1단계는 0과 1만 허용]

기존 프로젝트에 평가를 이식하는 방법은 침습도에 따라 4단계로 나뉩니다. 이 분류가 중요한 이유는, 어느 단계에서 어떤 방법을 써야 하는지 명확한 경계를 그어주거든요.

**레벨 0 — 반환값 래핑만 하기.** 기존 함수를 호출하는 얇은 래퍼 함수를 새로 작성하는 거예요. 기존 코드 파일을 열지 않습니다. 기존 코드 수정: 0줄. 이게 1단계에서 가장 권장하는 방식입니다.

**레벨 1 — 반환 직후 기록 추가.** 기존 함수의 마지막 `return` 바로 앞에 `monitor.record_task()`를 추가하는 거예요. 1줄에서 3줄 추가. 기존 파일을 열긴 하지만 최소한의 수정만 합니다. 1단계에서 허용하는 범위예요.

**레벨 2 — 내부 흐름에 훅 추가.** 함수 중간 단계에 측정 코드를 삽입하는 거예요. 로직은 안 바꾸지만 구조적인 수정이 들어갑니다. 이건 다음 챕터, 시스템 전체를 이해한 후에 하는 거예요.

**레벨 3 — 아키텍처 변경.** 에이전트 클래스를 상속하거나, 함수 인터페이스를 바꾸거나, 미들웨어를 통째로 삽입하는 수준이에요. 1단계에서는 절대 금지입니다.

오늘은 레벨 0과 레벨 1만 씁니다. 결론은 간단해요.

한 가지 더 짚고 넘어갈 게 있어요. 데코레이터 적용 가능한 상황과 불가능한 상황을 미리 파악해두는 것도 중요합니다. 함수가 `str`을 반환한다 — 레벨 0으로 `@eval_session.qa` 바로 적용. 함수가 `dict`나 객체를 반환한다 — 래퍼 함수에서 `str` 변환 처리 필요. 클래스 메서드거나 반환 구조가 복잡하다 — `create_taskresult()`로 직접 기록. 이 세 경우를 자신의 프로젝트에 대입해서 미리 측정점 후보를 분류해두면, 실제 이식 시간을 크게 줄일 수 있어요.

## [MAIN3] 첫 측정점을 고르는 세 가지 기준

[SLIDE: 측정점 선택 체크리스트 — 3가지 모두 만족해야]

지금 여러분 프로젝트에 함수가 수십 개 있을 거예요. 그중에서 첫 번째 측정점을 어떻게 고르느냐가 1단계의 성공을 좌우합니다. 잘못 고르면 30분이 아니라 3시간이 걸려요.

세 가지 기준이 있는데, 세 가지 다 만족하는 함수를 찾는 게 이상적이에요.

**기준 1: 입출력이 명확하다.** 파라미터 3개 이하, 반환값이 단일 타입이면 이상적입니다. `question: str` 받아서 `str` 반환하는 함수면 완벽해요. 반대로 `self`, `context`, `state`, `config`, `**kwargs` 이렇게 줄줄이 받으면서 `Optional[Response]` 반환하는 함수는 일단 패스. 내부 상태를 여러 군데서 읽고 쓰는 함수는 나중으로 미루세요. 지금 건드리면 이식이 아니라 고고학 발굴 작업이 됩니다.

**기준 2: 이미 성공 기준이 있다.** 기존 코드에 검증 로직이 있거나, "이 함수가 이걸 반환하면 성공"이라는 기준이 암묵적으로라도 존재해야 해요. 예를 들어, "답변이 300단어 이상이어야 한다", "출처가 2개 이상이어야 한다", "신뢰도가 0.7 이상이어야 한다" 이런 것들이요. 이 기준이 `ground_truth`와 `accuracy` 측정의 출발점이 됩니다. 심지어 ground_truth가 없어도 단어 수나 구조 기반으로 TCR을 측정할 수 있어요.

**기준 3: 독립적으로 호출 가능하다.** 다른 에이전트의 상태나 전역 변수에 의존하지 않고, 입력만 넘겨주면 단독으로 실행할 수 있어야 합니다. 이게 재현 가능한 평가의 기초예요. 아무리 좋은 함수라도 "실행하려면 먼저 다른 에이전트가 특정 상태여야 한다"는 조건이 붙으면 반복 실험이 어려워집니다.

흔한 선택 실수도 말씀드릴게요. "메인 오케스트레이터 함수를 측정하면 전체를 한 방에 볼 수 있지 않나?" — 안 돼요. 오케스트레이터는 내부 상태 의존성이 가장 많고, 반환값도 복잡한 경우가 많아요. 잎 노드, 즉 가장 말단에 있는 원자적 함수부터 시작하세요. 그 다음에 단계적으로 올라가는 거예요.

세 가지 다 만족하는 함수가 없다면요? 기준 1번, 입출력 명확한 함수만 만족해도 일단 시작하세요. 완벽한 첫 측정점은 없어요. 일단 측정을 시작하는 게 중요합니다.

[PAUSE]

## [MAIN4] 범용 레벨 0 패턴 — 어떤 프로젝트든 이 틀 안에 들어온다

[SLIDE: 범용 래핑 패턴 — QuickEval + @eval_session.qa]

자, 이론은 충분히 했으니 실제 코드 패턴 보겠습니다.

[CODE: generic_wrapper.py — 범용 레벨 0 래핑 패턴: (1) QuickEval 임포트 및 eval_session 생성, (2) 기존 함수 existing_function은 수정 없음, (3) @eval_session.qa 데코레이터가 붙은 measured_function 래퍼 작성 — result가 객체일 경우 .text 속성만 추출, str로 변환해서 반환, (4) 호출부에서 existing_function → measured_function으로 이름만 교체]

화면에 코드 보이시죠? 핵심만 짚겠습니다.

`QuickEval("eval_results/")` — 이 한 줄이 평가 세션을 열어줍니다. 결과 파일이 저장될 경로를 지정하는 거예요. 내부에서 `PerformanceMonitor`가 자동으로 초기화되고, 모든 트래커가 연결됩니다.

`@eval_session.qa` — 이 데코레이터가 붙은 함수는 호출될 때마다 자동으로 `TaskResult`가 생성되고, monitor에 기록됩니다. `task_type="qa"`로 설정된 거예요.

래퍼 함수 내부를 보시면, 기존 `existing_function`을 그냥 호출하고, 반환값에서 텍스트만 꺼내서 리턴합니다. `hasattr(result, "text")` 체크를 하는 건 반환값이 객체일 수도 있기 때문이에요. 객체면 `.text` 속성을 꺼내고, 아니면 `str()`로 변환합니다.

그러고 나서 기존 호출부에서 함수명만 바꿔주면 끝. `existing_function`이 있던 자리에 `measured_function`을 넣어주면 됩니다. 기존 코드 파일은 열지도 않았어요. 이 단순함이 핵심입니다.

복잡하게 만들면 이식 자체가 또 하나의 프로젝트가 되어버려요. 그러면 30분이 아니라 3일이 걸립니다. 단순하게, 최소한으로, 그게 1단계의 전략이에요.

## [MAIN5] 실전 이식 1 — QAAgent, 타이머 시작

[SLIDE: ⏱️ 타이머 START — QAAgent 레벨 0 이식 실습]

자, 여기서부터 실제 프로젝트에 적용합니다. 오늘 예제 프로젝트는 Lecture_forge라는 강의 생성 AI예요. 사용자가 강의 자료를 올리면 질문에 답변해주는 QAAgent가 있고, 섹션별 콘텐츠를 작성해주는 ContentWriter가 있습니다. 이 두 에이전트에 측정점을 삽입할 거예요.

먼저 QAAgent의 `answer()` 메서드에 세 가지 기준을 대입해볼게요.

입출력 명확한가요? `question: str` 받아서 `dict` 반환합니다. 딕셔너리 안에 `answer` 문자열, `sources` 리스트, `confidence` 숫자가 있어요. 명확합니다.

성공 기준이 있나요? 네, 코드 안에 이미 검증 로직이 있어요. 300단어 이상, 출처 2개 이상, 신뢰도 0에서 1 사이. 이게 ground_truth와 accuracy 측정의 출발점이 됩니다.

독립 호출 가능한가요? 네, `lecture_dir`만 있으면 단독으로 실행됩니다.

완벽한 첫 측정점이에요. 바로 이식 들어갑니다.

[CODE: cli/chat.py — QAAgent 레벨 0 이식 전후 비교: (수정 전) chat_command 함수 내부에서 qa_agent.answer(question) 호출 후 result["answer"] 출력하는 while 루프 / (수정 후) QuickEval 임포트 1줄 추가, eval_session = QuickEval("lecture_eval_results/", auto_save=True) 1줄 추가, _ctx = {} 클로저 변수 1줄 추가, @eval_session.qa 데코레이터 붙인 measured_answer 래퍼 함수 — result["answer"]만 반환하고 _ctx["sources"]에 sources 저장, while 루프에서 measured_answer 호출로 교체 — 총 6줄 추가, 기존 while 루프 로직 수정 0줄]

수정한 거 보이시죠? 총 6줄 추가입니다. 기존 로직 수정은 0줄이에요.

여기서 두 가지 포인트가 특히 중요합니다. 꼭 이해하고 넘어가세요.

**첫 번째, 왜 `result` 통째로 반환하지 않고 `result["answer"]`만 반환하냐고요?**

`@eval_session.qa` 데코레이터는 내부적으로 `@agent_eval(monitor, task_type="qa")`와 동일하게 동작합니다. 이 데코레이터는 함수의 반환값을 `TaskResult.response` 필드 — 타입이 `str`이에요 — 로 캡처해서 accuracy 점수를 계산해요. Token F1, Jaccard Similarity, LCS Ratio, Character Similarity, 이렇게 네 가지 지표를 조합한 점수를 냅니다.

만약 `result` 딕셔너리를 통째로 반환하면 어떻게 되냐고요? `str({"answer": "...", "sources": [...], "confidence": 0.9})` — 이 문자열이 response에 저장됩니다. 그러면 이 문자열과 ground_truth를 비교하게 되는데, 모든 accuracy 점수가 완전히 무의미해져요. 괄호, 따옴표, 딕셔너리 키 이름까지 다 비교 대상이 되니까요.

그래서 평가에 쓸 텍스트인 `answer`만 반환하고, 나머지 데이터인 `sources`와 `confidence`는 클로저 변수 `_ctx`를 통해 while 루프에서 접근할 수 있게 만드는 거예요. 원래 기능은 100% 유지하면서 평가는 정확하게 하는 방법입니다.

**두 번째, 왜 `auto_save=True`가 필수냐고요?**

`while True` 루프를 생각해보세요. 이 루프는 끝나지 않잖아요. 루프 밖에 `eval_session.save()`를 쓰면 그 줄은 절대 실행되지 않습니다. 프로그램이 정상 종료될 일이 없으니까요. 그럼 30분 동안 쌓인 채팅 데이터가 어디에도 저장이 안 된 채로 프로세스가 죽으면 전부 날아갑니다.

`QuickEval("경로/", auto_save=True)`로 생성하면 10건마다 자동으로 `save_to_file()`이 호출돼요. 채팅 세션 중간에 서버 재시작하거나 강제 종료해도 최대 9건 치만 날아가고, 나머지는 다 보존됩니다. 서버 프로세스, 스트리밍 세션, long-running 세션 — 이런 상황에선 `auto_save=True`를 무조건 습관처럼 쓰세요.

타이머 확인해보면 — 여러분이 직접 해보시면 실제로 10분이면 충분합니다.

## [MAIN6] 실전 이식 2 — ContentWriter, 위임 어댑터 패턴

[SLIDE: 위임 어댑터 패턴 — Pydantic 모델 반환 시의 해법]

두 번째 측정점, ContentWriter입니다. 얘는 상황이 조금 달라요.

ContentWriter의 `write_section()` 메서드는 `SectionContent`라는 Pydantic 모델을 반환합니다. `@eval_session.qa` 데코레이터는 `str` 반환을 기대하니까 직접 붙일 수가 없어요.

선택지가 두 가지 있어요. 레벨 1 방식으로 `agent.py`를 직접 수정하거나, 아니면 기존 파일을 전혀 건드리지 않으면서도 완전한 측정이 가능한 방법을 쓰거나. 저는 두 번째를 추천합니다. 이게 **위임 어댑터 패턴**이에요.

아이디어는 정말 간단합니다. 기존 에이전트 인스턴스를 감싸는 어댑터 클래스를 별도 파일에 새로 작성하는 거예요. 어댑터가 원본 메서드를 호출하고, 결과를 `monitor`에 기록한 뒤, 원래 반환값을 그대로 돌려줍니다. 계측하지 않는 나머지 메서드와 속성은 `__getattr__`로 원본에 투명하게 위임해요.

[CODE: src/lecture_forge/eval/adapters.py — ContentWriterAdapter 클래스 전체: __init__에서 원본 agent, monitor, learning_objectives 주입 / write_section()에서 time.perf_counter()로 측정 시작, try 블록에서 self._agent.write_section() 호출, except에서 has_error와 error_msg 기록, finally 블록에서 create_taskresult() 호출 후 self._monitor.record_task() — content_text는 result.markdown_content 추출, ground_truth는 section.learning_outcomes 조인, extra에 phase·section_id·word_count 포함 / 메서드 끝에서 원래 result 그대로 반환 / __getattr__로 나머지 속성 투명 위임]

코드에서 특히 주목하실 부분 세 가지를 짚겠습니다.

첫째, **try/finally 구조**입니다. `write_section()`이 예외를 던져도 `finally` 블록은 반드시 실행돼요. `has_error=True`인 TaskResult가 monitor에 기록됩니다. 이게 Gate C — Reliability의 FaultTolerance 측정에 포함돼요. 정상 케이스만 측정하면 실제 에러 복구율을 알 수가 없잖아요. 오류가 났을 때의 케이스까지 자동으로 기록해주는 구조가 이 `try/finally`입니다.

둘째, **extra 딕셔너리**입니다. `phase`, `section_id`, `word_count`를 담아서 넘기는 게 보이시죠? 이게 나중에 Gate G의 Observability에 연결됩니다. 어느 단계에서 얼마나 시간이 걸렸는지, 섹션별 단어 수 분포는 어떤지 — 이런 것들을 나중에 분석할 때 이 extra 데이터가 있어야 가능해요. 지금 당장 쓰지 않더라도, 측정할 때 같이 넣어두는 게 습관이에요.

셋째, **`__getattr__` 투명 위임**입니다. 이게 위임 어댑터 패턴의 핵심이에요. `ContentWriterAdapter`는 `write_section()` 하나만 계측합니다. 나머지 메서드와 속성, 예를 들어 `get_model_info()`라든가 `is_ready`라든가 — 이런 것들은 `__getattr__`가 자동으로 원본 에이전트로 넘겨줘요. 어댑터를 씌운 후에도 기존 코드가 어댑터를 원본 에이전트처럼 쓸 수 있습니다.

[CODE: cli/commands/create.py — 진입점에서 어댑터 적용: 기존 ContentWriterAgent 인스턴스 생성 코드는 그대로 유지, 그 바로 아래에 _eval_monitor가 있을 때만 ContentWriterAdapter로 교체하는 2줄 추가 — if _eval_monitor: writer = ContentWriterAdapter(writer, _eval_monitor, curriculum.learning_objectives)]

진입점 코드를 보시면, `_eval_monitor`가 있을 때만 어댑터로 교체합니다. 모니터가 없으면 기존 `writer` 그대로 씁니다. 이게 opt-in 설계예요. 평가 모드를 켜지 않으면 기존 코드와 완전히 동일하게 동작합니다. QA팀에서 평가 파이프라인 돌릴 때만 `_eval_monitor`를 넘겨주면 되고, 프로덕션 배포 시엔 `None`으로 두면 오버헤드가 전혀 없어요.

이 방식의 장점을 정리해볼게요.

`ContentWriterAgent`의 소스 파일을 열지 않습니다. 어댑터를 씌운 후에도 `writer.write_section()`의 인터페이스와 반환값은 완전히 동일합니다. 어댑터 없이도 코드가 그냥 돌아갑니다.

수정한 것: `eval/adapters.py` 새 파일 하나 + `create.py`에 어댑터 교체 2줄. 기존 파일 수정: 0줄. `content_writer/agent.py`는 열지도 않았어요. 파일 목록에서 찾지도 않았습니다.

## [MAIN7] 첫 실행 — 어떤 숫자가 보이는가

[SLIDE: 첫 측정값 해석 — 기준선이 생겼다는 것의 의미]

자, 두 개의 측정점을 삽입했습니다. 이제 Lecture_forge를 실행하고 나서 실제로 어떤 숫자들이 생기는지 볼게요.

[CODE: 터미널 실행 — python -m lecture_forge chat ./lectures 실행 후 질문 10건 입력, 종료 후 lecture_eval_results/ 디렉토리 확인, quickeval.json 또는 evaluation_YYYYMMDD_HHMMSS.json 파일 생성 확인]

`lecture_eval_results/` 디렉토리를 열어보면 JSON 파일이 생겼을 거예요. 그 안에 이런 숫자들이 있습니다.

**Task Completion Rate, TCR.** "에이전트가 요청받은 작업을 완료했는가"의 비율이에요. 대화 10건 중 몇 건이 정상적으로 답변을 돌려줬는지. 처음 측정해보면 "어, 생각보다 낮네?" 하실 수 있어요. 그게 정상입니다. 지금까지 몰랐던 거니까요. 그리고 그걸 발견했다는 게 이미 성과입니다.

**accuracy.** Token F1, Jaccard Similarity, LCS Ratio, Character Similarity를 가중 평균한 점수예요. ground_truth를 제공했다면 이 점수가 의미 있고, 비워뒀다면 일단 TCR과 응답 품질 점수 쪽을 봐야 합니다. ground_truth가 없어도 측정을 시작할 수 있다는 게 agent-evaluator의 특징이에요.

**execution_time.** 각 호출마다 몇 초 걸렸는지가 다 찍혀 있어요. 10건 정도 쌓이면 평균이 나오고, 50건 이상 쌓이면 P50, P95, P99 같은 레이턴시 분포를 볼 수 있게 됩니다. "평균 3초인 줄 알았는데 P99가 12초야" — 이런 걸 발견하는 게 이 측정의 가치예요.

ContentWriter 쪽에선 `word_count` 같은 extra 데이터도 함께 저장돼 있어요. 섹션별로 몇 단어가 나왔는지 분포를 볼 수 있고, `phase` 태그로 콘텐츠 작성 단계의 지연이 얼마인지도 나중에 분석할 수 있습니다.

대시보드로도 확인해볼 수 있어요. `agent-eval dashboard` 명령 하나면 FastAPI 서버가 뜨면서 결과를 시각화해줍니다. 숫자를 직접 JSON에서 읽는 것보다 훨씬 직관적이에요. Gate A부터 G까지 각각 어느 단계에서 어떤 점수가 나왔는지 카드 형태로 바로 볼 수 있거든요.

이 시점에서 중요한 마음가짐을 하나 말씀드릴게요. **1단계의 숫자들이 지금 당장 완벽한 인사이트를 주지 않아도 괜찮습니다.** 그게 맞아요. 1단계의 목표는 완벽한 분석이 아니라 **기준선을 확보하는 것**이에요. 지금 TCR이 72%라면, 다음 배포 후에 이게 올라갔는지 내려갔는지 비교할 수 있게 됐다는 게 핵심입니다.

이전에는 "느낌상 나아진 것 같은데요" 였다면, 이제는 "TCR이 72%에서 81%로 올랐고 P95 레이턴시는 8.2초에서 4.1초로 반으로 줄었습니다" 라고 말할 수 있어요. 팀 리뷰에서, 이해관계자 보고에서, 배포 결정에서. 숫자로 얘기할 수 있게 된 거예요.

## [MAIN8] 이식하면서 자주 하는 실수 — 그리고 해결책

[SLIDE: 이식 실수 TOP 3 — 반드시 피해야 할 것들]

마지막으로, 이 과정에서 자주 하는 실수 세 가지만 짚겠습니다. 저도 처음에 다 겪어봤던 것들이에요.

**실수 1: dict 통째로 반환하기.** 방금 QAAgent에서 설명드렸죠. `result["answer"]`가 아니라 `result` 딕셔너리 통째로 반환하면 accuracy 점수가 전부 쓰레기가 됩니다. 데코레이터가 붙은 함수는 항상 "평가에 쓸 텍스트"만 반환해야 해요. 나머지 데이터가 필요하면 클로저나 별도 저장소를 활용하세요.

**실수 2: long-running 세션에서 `auto_save` 빼먹기.** `while True` 루프, FastAPI 엔드포인트, 배치 처리 스크립트 — 이런 상황에서 `auto_save=True` 없이 이식하면, 나중에 결과 파일을 열었을 때 거의 비어 있거나 아예 파일 자체가 없는 상황을 만나게 됩니다. "이상하다, 분명히 실행했는데" — 이 상황을 만나신 분들, 거의 대부분이 이 실수예요. `auto_save=True`는 선택이 아닙니다.

**실수 3: 첫 이식에 측정 대상을 너무 많이 잡기.** "어차피 하는 김에 다 하자" — 이 생각이 1단계를 실패하게 만드는 원인 1위예요. 처음엔 딱 2개, 많아도 3개만 잡으세요. QAAgent 하나, ContentWriter 하나. 이것만 해도 충분히 의미 있는 데이터가 나옵니다. 10개 측정점을 동시에 이식하려다가 중간에 지쳐서 하나도 못 끝내는 것보다, 2개를 완벽하게 끝내는 게 훨씬 낫습니다.

그리고 하나 더 — 이식 후에 기존 테스트를 반드시 돌려보세요. 레벨 0 이식이라 기존 로직을 건드리지 않았다지만, 래퍼 함수 작성 과정에서 반환 타입이 바뀌진 않았는지, 기존 호출부에서 기대하던 값이 제대로 오는지 한 번 확인하는 게 안전해요. `pytest`를 이미 쓰고 계신다면 `pytest --collect-only`로 기존 테스트가 잘 인식되는지 먼저 확인하고, 풀 테스트 한 번 돌려보시면 됩니다.

이 세 가지 실수만 피해도 30분 안에 첫 측정값 뽑는 거 충분히 됩니다.
