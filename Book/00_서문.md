# 서문: AI 에이전트 평가, 왜 지금인가

---

## 이 책이 필요한 이유

소프트웨어 세계는 지금 조용하고도 근본적인 전환점을 맞이하고 있습니다. 기존 소프트웨어는 결정론적입니다. 함수에 동일한 입력을 넣으면 항상 동일한 출력이 나옵니다. 테스트도 그 원칙 위에 세워졌습니다. `assert result == expected` 한 줄이면 충분했습니다.

AI 에이전트는 다릅니다. 에이전트는 도구를 선택하고, 외부 API를 호출하고, 여러 단계에 걸쳐 스스로 계획을 수정합니다. 같은 질문에도 매번 다른 경로로 답에 도달합니다. 때로는 환각(hallucination)으로 틀린 정보를 자신감 있게 전달하고, 때로는 허가되지 않은 도구를 실행하거나 민감한 데이터를 출력에 포함시키기도 합니다. `assert`는 이 복잡성을 포착하지 못합니다.

이 책은 그 간극을 메우기 위해 쓰였습니다. AI 에이전트를 프로덕션에 배포하기 전에 **무엇을**, **어떻게** 평가해야 하는지를 실무 중심으로 다룹니다. 이론보다 코드, 개념보다 실제 동작하는 예시를 우선합니다.

## Harness Engineering이란

이 책은 **Harness Engineering**이라는 관점으로 AI 에이전트 평가를 다룹니다.

기존 소프트웨어 테스팅은 "버그가 없는가"를 묻습니다. Harness Engineering은 다른 질문을 던집니다. **"이 에이전트는 배포해도 되는가?"** 그리고 그 답을 코드로 선언합니다.

```python
# Harness Engineering의 핵심 패턴 — Config-as-Code
from agent_evaluator import QuickEval

eval = QuickEval("results/")

@eval.qa
def agent(question, ground_truth=""):
    return my_agent.run(question)

# 배포 기준을 코드로 선언하고, 위반 시 배포를 자동 차단
eval.gate(tcr=85, accuracy=70)
```

Harness Engineering의 3요소:
- **Tracker** — 에이전트 실행 중 지표를 자동 관찰·기록
- **Config** — "이 에이전트는 어떤 조건에서 배포될 수 있는가"를 코드로 선언
- **Gate** — Config 위반 시 `success=False` → `HarnessEvaluationGate`로 종합 판정

이 세 요소가 협력하면 에이전트의 배포 기준이 문서나 관행이 아닌 **실행 가능한 코드**가 됩니다. 에이전트가 자신의 배포 기준을 소유하는 것입니다.

## 이 책이 다르게 생각하는 것들

이 책은 AI 에이전트 평가에 대해 몇 가지 전제를 가지고 있습니다. 기존 소프트웨어 테스팅 관점과 다르게 생각하는 부분입니다.

**1. 품질은 숫자 하나가 아니라 분포다**

`accuracy = 0.85`는 완전한 정보가 아닙니다. 같은 0.85라도 분산이 작으면 안정적인 에이전트, 분산이 크면 예측 불가능한 에이전트입니다. 이 책은 Wilson Score Interval 같은 확률론적 임계값 설정을 다룹니다.

**2. AI는 AI가 가장 잘 평가한다**

사람이 수백 개의 에이전트 응답을 읽으며 품질을 채점하는 것은 현실적이지 않습니다. LLM Judge는 선택 사항이 아니라 Harness Engineering의 핵심 부품입니다. 이 책은 LLM Judge를 `@agent_eval(enable_llm_judge=True)` 한 줄로 활성화하는 방법을 다룹니다.

**3. 배포 전 테스트만으로는 충분하지 않다**

에이전트가 사용하는 LLM 모델이 업데이트될 수 있습니다. 프롬프트가 바뀔 수 있습니다. 외부 데이터가 변할 수 있습니다. 이 책은 코드·모델·프롬프트·데이터, 4가지 변경 소스를 기준으로 드리프트를 감지하고 Harness를 재보정하는 방법을 다룹니다.

**4. 출현 행동은 탐지 목록 밖에서 온다**

SQL Injection 패턴 목록이 아무리 방대해도, 목록에 없는 공격은 통과합니다. 의미 기반 탐지가 패턴 매칭과 반드시 함께해야 합니다. 이 책은 보안 경계(Group E)에서 2계층 탐지를 다룹니다.

**5. 평가는 배포 전에 끝나지 않는다**

프로덕션 에이전트의 평가는 배포 후에도 계속됩니다. `agent-eval trend`로 순차 실행 결과를 추적하고, `RunTrendAnalyzer`로 회귀를 조기 감지하며, 평가 결과를 프롬프트 개선에 환류하는 자기개선 루프가 완전한 Harness Engineering입니다.

## 실습 환경 안내

이 책의 모든 코드 예시는 **Python 3.8 이상** 환경에서 실행됩니다. 실습을 위해 다음 환경이 필요합니다.

```bash
# 기본 설치 — LLMJudge · 대시보드 · OTEL 모니터링 · PDF 포함
pip install agent-evaluator

# 실습 확인
agent-eval --version
# → agent-evaluator 0.8.4
```

LLM API를 사용하는 예시에서는 OpenAI 또는 Anthropic API 키가 필요합니다. 프로젝트 루트에 `.env` 파일을 만들고 키를 설정하면 됩니다.

```bash
# .env
OPENAI_API_KEY=sk-...
ANTHROPIC_API_KEY=sk-ant-...
```

API 키 없이도 Group A~F의 대부분 지표는 알고리즘 기반으로 즉시 동작합니다. LLM Judge(Group G의 일부)만 API 키가 필요합니다.

## Agent-Evaluator SDK 소개

이 책에서 사용하는 **Agent-Evaluator**는 AI 에이전트 Harness Engineering을 위해 설계된 오픈소스 Python SDK입니다.

- **버전**: v0.8.3 (Beta)
- **라이선스**: MIT
- **지원 Python**: 3.8 ~ 3.13

핵심 설계 원칙은 세 가지입니다. 첫째, **외부 의존성 없는 네이티브 평가**입니다. 58개 지표 중 대부분은 OpenAI나 Anthropic API 없이 로컬에서 즉시 계산됩니다. 둘째, **데코레이터 한 줄**로 평가를 시작할 수 있는 최소 마찰 설계입니다. 셋째, **Config-as-Code 패턴**으로 배포 기준을 코드로 선언하고 Gate로 자동 판정합니다.

58개 지표는 7개의 품질 차원(Group A-G)으로 구성됩니다. 각 Group은 독립적인 Harness Config와 Tracker를 가집니다. `HarnessEvaluationGate`가 7개 Group을 한 번에 평가해 최종 배포 판정을 내립니다.

## 각 파트 간략 소개

**Part I — 기초**: AI 에이전트 Harness Engineering의 개념, SDK 설치와 첫 배포 판정 경험. 이 책의 출발점입니다.

**Part II — Harness 지표 체계**: 58개 지표를 Group A-G 기준으로 심화 학습합니다. 각 Group의 Tracker(측정)와 Config(기준 선언)를 함께 다룹니다. 지표별 레퍼런스로 활용할 수 있습니다.

**Part III — 개발자 가이드**: 데코레이터·프레임워크 통합·평가 데이터 설계를 다룹니다. LangChain, LangGraph, CrewAI, AutoGen 등 21개 프레임워크와 Harness를 연결하는 실전 예시를 제공합니다.

**Part IV — QA 관리자 가이드**: 임계값 설정, 대시보드 운영, 알림 시스템, 주간·월간 품질 리뷰를 다룹니다. Config-as-Code 기준 선언과 Harness Gate 운영이 핵심입니다.

**Part V — 프로덕션 운영**: CI/CD Harness Gate, Phoenix 실시간 모니터링, 프로덕션 배포 전략, 지속 평가·자기개선 파이프라인을 다룹니다. 드리프트 감지와 자기개선 루프가 이 파트의 핵심입니다.
