# eval-run-directory-hygiene

Archivist 실습서(워크북) Ch 22·35에서 같은 종류의 문제를 두 번 겪었다 —
**Agent-Evaluator의 비교/추세 도구는 "비교 대상이 서로 같은 목적의
실행이다"를 전제로 하는데, 그 전제가 깨지면 조용히 틀린 답을 낸다.**

- Ch 22: `agent-eval gate --baseline`/`--baseline-version`은 `--save-
  baseline`이 만드는 **평평한 요약 JSON**을 기대하는데, `--baseline-
  result`/`diagnose --baseline`은 **전체 원시 결과(`tasks[]` 포함)**를
  기대한다 — 모양이 다른 파일을 잘못된 플래그에 넣으면 예외 없이 그냥
  회귀를 0건으로 낸다.
- Ch 35: `agent-eval trend results/final/`이 골든셋 평가·PII 테스트·
  멀티에이전트 실측처럼 **성격이 전혀 다른 실행들**이 한 디렉터리에
  섞인 걸 "형제 실행"으로 오인해, TCR이 "100%→75%로 하락 중"이라는
  가짜 회귀를 경고했다.

두 사례 모두 도구가 예외를 던지지 않았다 — 그냥 잘못된 답(회귀 0건,
또는 가짜 회귀)을 냈다. **결과 파일의 모양과 디렉터리 구성 자체가
정답에 영향을 준다**는 것이 이 스킬이 다루는 핵심이다.

## 언제 발동하는가

- `agent-eval trend`/`abtest`/`gate --baseline*`의 출력이 직관과 안
  맞을 때(회귀가 없어야 하는데 뜨거나, 있어야 하는데 안 뜨거나)
- 새로운 결과 파일 디렉터리를 만들기 전에 미리 구성 규칙을 정할 때

## 절차 (3단계)

1. **파일 모양을 먼저 맞춘다.** `--baseline`류 플래그마다 기대하는
   JSON 모양이 다르다는 것을 SDK 문서/CLI `--help`로 확인하고, 필요한
   모양의 파일을 정확히 그 플래그에 넣는다(`--save-baseline`으로 만든
   요약과 원시 결과 파일을 섞지 않는다).
2. **디렉터리를 목적별로 분리한다.** `trend`/`abtest`에 넘길 디렉터리는
   **같은 평가 하네스의 형제 실행만** 모은다 — 적대적 테스트, 멀티
   에이전트 실측, 재현성 반복 실행처럼 목적이 다른 결과는 별도
   서브디렉터리(예: `results/final/golden_snapshots/`)로 분리한다.
3. **의심스러운 신호는 원인을 다시 진단한다.** 회귀/추세 결과가 이상하면
   "표본 부족"과 "이종 데이터 혼합"은 겉보기엔 비슷해도 원인이 다르다
   — 진단이 바뀌었으면 "여전히 이상하다"로 뭉뚱그리지 말고 새 원인을
   근거와 함께 다시 적는다(Ch 35에서 실제로 원인이 바뀐 사례).

## 이 스킬이 하지 않는 것

- `trend`/`abtest`의 내부 로직을 바꾸지 않는다 — 입력을 그 도구의
  전제에 맞게 정리하는 절차다(원칙4).
- 디렉터리 구조를 자동으로 재배열하지 않는다 — 어떤 실행이 "형제"인지
  판단은 사람이 한다(도구가 실행 메타데이터만으로 목적을 추론할 근거가
  없다).

> 절차 정본: 이 워크북 Ch 22(`--baseline` 계열 모양 불일치)·
> Ch 35(`trend`의 이종 디렉터리 오탐, `results/final/golden_snapshots/`
> 분리로 해소) — 두 건 모두 실측으로 확인된 독립 사례.
