# threshold-realism-review

방법론서 §30은 "이 기록이 5회 넘게 같은 사유로 반복되면, 그건 애매한 게
아니라 임계값이 현실과 안 맞는 것"이라고 원칙을 선언하고 §31.6으로
넘긴다고만 적어뒀다 — **그런데 "누가, 무엇을 보고, 어떻게 새 임계값을
정하는지"의 실행 절차는 어디에도 없었다.** 이 스킬이 그 공백을 채운다
(Harness Autopilot 설계서 §9 마찰 #5).

## 언제 발동하는가

`agent-eval gate --hold-on-undecided`가 exit 75를 낸 기록을 훑어(배포
결정 원장, `agent-eval decisions list`), **같은 Gate·같은 사유로 5회
넘게** 반복됐는지 확인한다. 5회 미만이면 그냥 애매한 개별 사례로 두고
넘어간다 — 성급하게 임계값을 흔들지 않는다.

## 절차 (4단계 — 방법론서 §5.5 "누가 조정하는가"의 4단계 파이프라인 재사용)

1. **설계자**가 반복된 5건의 `undecided_reason`과 Wilson CI 폭을
   모아 "이 임계값이 애초에 통계적으로 달성 가능한 수준인가"를 판단한다
   (표본 크기 대비 목표선이 너무 타이트했을 가능성부터 본다).
2. **개발자**가 그 5건의 실제 Gate 점수 분포를 `agent-eval trend`로
   확인해, 정말 "경계선 근처에서 계속 흔들리는" 것인지 아니면 다른
   회귀가 숨어있는 것인지 구분한다.
3. **QA·거버넌스 담당(하나 역할)**이 새 임계값 후보를 RCA 절차(5 Whys,
   `agent-eval diagnose`)로 정당화하고, 낮추는 방향의 조정이면 제안자와
   다른 사람이 확인한다는 방법론서 §5.5의 규칙을 그대로 적용한다.
4. **조직**이 확장 속도를 정한다 — 임계값을 낮췄다면 그 사실과 근거를
   `.aoo/decisions.jsonl`에 `overridden`이 아니라 새 `.aoo/targets.json`
   갱신으로 남긴다(`agent-eval target set`). 임계값 변경 자체는 게이트
   판정이 아니므로 결정 원장과 다른 채널이다.

## 이 스킬이 하지 않는 것

- 임계값을 자동으로 낮추지 않는다 — 4단계 전부 사람이 판단한다.
- Gate 채점 로직을 바꾸지 않는다(원칙4 — 이미 있는 Gate A–G 채점 엔진을
  다시 만들지 않는다) — `.aoo/targets.json`의 숫자만 바뀐다.
