# Spec-Driven 핵심 산출물 템플릿 (4대 산출물 + Gate 매핑 초안)

이 스킬은 《하니스 메서드》 §15(요구사항 분석)가 정의한 절차를 실행 가능한 템플릿으로 제공한다. Spec-Driven은 SDK 기능이 아니라 팀 방법론이라 SDK 가이드에는 대응하는 챕터가 없다 — 이 책 §15가 유일한 정의처다. 새 기능을 만들기 **전에**, 이 순서대로 채운다.

> ⚠️ **이 스킬은 《하니스 메서드》의 6대 산출물(§2 ⑤: Spec·실패 모드 카탈로그·골든셋·의존관계 지도·ADR·세션 목표 템플릿) 전부를 담지 않는다.** 이 스킬이 만드는 것은 그중 4개(Spec·실패 모드 카탈로그·골든셋·세션 목표 템플릿)뿐이다 — 의존관계 지도(§16)는 실제 코드베이스를 grep해야 나오는 산출물이라 빈 템플릿으로 채울 수 없고, ADR(§17)은 이 스킬이 아니라 별도의 `adr-template` 스킬(§27)이 맡는다. 아래 "3) Gate 매핑 초안"은 6대 산출물에 속하지 않는 보너스 절이다 — 산출물 개수(4개)에 포함하지 않는다.

## 0) 기존 자산 검색 (건너뛰지 말 것)

먼저 확인한다 — 이미 있는 걸 모르고 새로 만들면 그대로 기술부채가 된다. 아래 세 곳을 5분 안에 훑는다(《하니스 메서드》 §15.0 참고).

```bash
# ① 팀 공유 설정 저장소의 커밋 이력 — 유사한 Tool/Config가 이미 추가된 적이 있는가
git log --oneline -- <관련 디렉토리>/

# ② 기존 Config 클래스·Tool 정의 grep — 새로 만들기 전에 이미 있는지 먼저 확인
grep -rn "class\|<관련 필드명>" <관련 디렉토리>/*.py
```

```python
# ③ 관련 시도 이력 확인 — 과거 세션이 이미 겪은 문제라면 그 해결책을 재사용
search_violations(DB_PATH, "<관련 키워드>")
```

이미 있는 실패 모드 카탈로그·Gate 매핑이 있다면 새로 만들지 않고 재사용·확장한다. 세 확인 모두 결과가 없었다면 그것도 유효한 결과다 — "검색 없이 바로 시작"과는 다른, 검증된 출발점이다.

## 1) Spec (구조·기능·비기능 요구사항)

```markdown
# SPEC — [기능명]

## 배경
[이 기능을 왜 만드는지 — 요청 배경 한두 문장]

## 구조 요구사항
- 관여 모듈/인터페이스: [여기에 채운다]

## 기능 요구사항 (EARS 표기법)
- **SPEC-001**: The system shall [정상 동작].
- **SPEC-002**: When [조건], the system shall [동작].
- **SPEC-003**: [NEEDS CLARIFICATION: 미해결 항목 — 아래 "완료 조건"을 통과하려면 반드시 해소한다]

## 비기능 요구사항
- **SPEC-NFR-001**: [예: 지연·보안 제약] → 해당 Gate D/E Config로 연결

## 상태
초안
```

이 Spec의 "기능 요구사항" 중 IF...THEN(Unwanted behavior) 패턴만 뒤집으면 아래 2)의 실패 모드 카탈로그가 된다 — 별개 문서가 아니라 파생 관계다.

|---|---|---|
| (1)의 SPEC-NNN을 뒤집어 채운다 | | |

## 3) Gate 매핑 초안 (설계자가 §17에서 확정하는 예비 스케치)

Gate 매핑을 최종 확정하는 것은 분석가가 아니라 **설계자의 몫**이다(《하니스 메서드》 §17). 이 절은 분석 세션이 손을 떼기 전에 다음 사람(설계자)에게 넘길 **1차 추정**만 남긴다 — 아래 표가 최종 결정이 아니라는 것을 팀이 오해하지 않도록, 넘길 때 "초안"이라는 상태를 명시한다.

| 실패 모드 | Gate(추정) | 배치 vs 실시간(추정) |
|---|---|---|
| (2)의 각 행을 여기로 옮긴다 | | 실행 전 차단이 필요하면 LiveGuardrail, 사후 집계로 충분하면 배치 Gate |

> 이 표를 실제 Config 클래스명(`HallucinationDetector`·`OutputLeakageDetector`·`ReproducibilityConfig`·`LoopDetectionConfig` 등)까지 채운 완성 예시는 《하니스 메서드》 §18.4(사내 문서 Q&A 시나리오)의 "Gate 매핑 초안" 표를 참고하라 — 빈 템플릿만으로 감이 안 잡힐 때 그 구체성의 기준으로 삼는다.

## 4) 최소 골든셋

```python
golden_cases = [
    # {"input": ..., "expected": ...},  # 어느 SPEC-NNN에서 왔는지 주석으로 남긴다
]
```

## 5) 세션 목표 템플릿

```
목표: [무엇을 만드는가]
완료 조건:
  1. [실패 모드 카탈로그에서 나온 검증 항목]
금지: [스코프 밖 행동]
```

## 완료 조건

- 4개 산출물(Spec·실패 모드 카탈로그·골든셋·세션 목표 템플릿)이 모두 채워졌다 — Gate 매핑 초안은 산출물이 아니라 다음 단계로 넘기는 예비 스케치이므로 이 개수에 포함하지 않는다.
- Spec의 `[NEEDS CLARIFICATION]` 태그가 전부 해소됐거나, **누가·언제 해소할지가 명시된 채 다음 단계로 위임**됐다(예: "§17에서 설계자와 확정한다") — 담당자·시점 없이 방치된 태그만 미해결로 본다(《하니스 메서드》 §15.1 참고).
- 사람이 이 초안을 직접 검토했다(모델 크기와 무관하게 항상 필요 — 《하니스 메서드》 §2 참고).
