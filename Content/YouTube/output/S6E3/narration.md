## [MAIN1] 이식의 제1원칙: 측정과 수정은 분리한다

[SLIDE: 이식 제1원칙 — 아무것도 깨지 않는다]

자, 먼저 질문 하나 드릴게요. 기존 프로젝트에 뭔가 새로운 코드를 붙이다가, 오히려 기존 기능을 망가뜨린 경험이 있으신 분? 아마 다들 한 번씩은 있으실 겁니다.

평가 코드를 이식할 때 제일 흔하게 일어나는 실수가 바로 이겁니다. "어, 평가하는 김에 이 부분도 리팩터링해볼까?" 라는 생각이 드는 거예요. 함수 인터페이스를 슬쩍 바꿔보거나, 로그를 남기려고 기존 흐름에 분기를 하나 추가하거나. 측정 코드를 넣으면서 동시에 내부 로직에도 손을 대기 시작하는 겁니다.

그러면 어떻게 될까요? 나중에 버그가 생겼을 때 "이게 평가 코드 때문인가, 아니면 내가 리팩터링한 것 때문인가"를 도무지 구분할 수 없게 됩니다. 측정이 오히려 시스템을 불안정하게 만드는, 아이러니한 상황이 생기는 거죠.

그래서 1단계의 원칙은 딱 하나입니다.

**기존 코드의 입력과 출력을 바꾸지 않는다. 반환값만 관찰한다.**

이것을 "레벨 0 침습"이라고 부릅니다. 함수가 무엇을 받고, 무엇을 반환하는지만 봅니다. 내부를 바꾸지 않습니다. 측정과 수정은 완전히 분리하는 겁니다. 이 원칙 하나를 지키는 것만으로도 1단계 이식에서 생기는 문제의 80%를 예방할 수 있습니다.

## [MAIN2] 침습도 레벨 4단계 — 지금은 0과 1만

[SLIDE: 침습도 레벨 0–3 — 1단계는 0과 1만 허용]

기존 프로젝트에 평가를 붙이는 방법을 침습도 기준으로 4단계로 나눠볼게요. 이 분류를 머릿속에 넣어두면, 나중에 "지금 내가 무리하고 있는 건 아닌가"를 스스로 체크할 수 있습니다.

**레벨 0** — 반환값 래핑만 합니다. 기존 함수를 호출하는 얇은 래퍼 함수를 새로 작성하는 거예요. 기존 코드 파일을 아예 열지 않습니다. 오늘 주로 다룰 방식이고, 1단계의 권장 방식입니다.

**레벨 1** — 기존 함수의 마지막 `return` 직전에 `monitor.record_task()` 호출을 한두 줄 추가합니다. 최소한의 수정이에요. 1단계에서 허용하는 수준입니다.

**레벨 2** — 기존 함수의 중간 단계에 측정 코드를 삽입합니다. 로직 자체는 바꾸지 않고 추적만 하지만, 구조적인 수정이 들어갑니다. 다음 챕터인 Ch25에서 다룹니다.

**레벨 3** — 에이전트 클래스를 상속하거나, 함수 인터페이스를 바꾸거나, 미들웨어를 삽입하는 수준입니다. 1단계에서는 절대 가면 안 됩니다.

오늘은 레벨 0과 레벨 1만 씁니다. 기억해두세요. 지금 단계에서 레벨 2 이상으로 손을 뻗고 싶은 충동이 생긴다면, 그건 범위를 벗어난 겁니다. 타이머가 아직 돌고 있다는 사실을 기억하세요.

## [MAIN3] 오늘 쓸 핵심 도구 — QuickEval, PerformanceMonitor, create_taskresult

[SLIDE: 핵심 도구 3종 — 뭘 언제 쓰는가]

코드로 넘어가기 전에, 오늘 실제로 쓸 도구들을 빠르게 짚고 넘어갈게요. Python 개발자 여러분이면 API 이름만 봐도 금방 감이 오실 겁니다.

첫 번째는 **QuickEval**입니다. 평가 세션을 가장 간단하게 시작하는 Facade예요. `QuickEval("results/")` 한 줄이 전부입니다. 그 다음에 `@eval_session.qa` 같은 데코레이터를 함수에 붙이면, 그 함수가 호출될 때마다 자동으로 결과가 기록됩니다. 단, 이 데코레이터는 함수가 `str`을 반환해야 합니다. 이 조건만 맞으면 레벨 0 래핑에 딱 맞는 도구입니다.

두 번째는 **PerformanceMonitor**입니다. 보안 스캔이나 Harness Gate Config 같은 더 세밀한 설정이 필요할 때 직접 사용합니다. Ch25에서 본격적으로 다룰 예정이에요. 오늘은 위임 어댑터 패턴에서 한 번 등장합니다.

세 번째는 **`create_taskresult()` 헬퍼**입니다. 데코레이터를 직접 붙이기 어려운 상황, 예를 들어 함수가 `dict`나 Pydantic 모델을 반환하는 경우, 수동으로 결과 한 건을 기록할 때 씁니다. 내부적으로 점수도 자동 계산해줘서 편합니다.

그럼 어떤 상황에 무엇을 쓰는지 딱 정리하면 이렇습니다. 함수가 `str`을 반환하면 `@eval_session.qa`를 바로 붙입니다. 함수가 다른 타입을 반환하면 오늘 후반부에서 다룰 **위임 어댑터 패턴**을 씁니다. 클래스 메서드나 복잡한 반환 구조라면 `create_taskresult()`로 수동 기록합니다. 이 세 가지 케이스가 현실에서 마주치는 상황의 거의 전부입니다.

## [MAIN4] 첫 측정점을 고르는 세 가지 기준

[SLIDE: 첫 측정점 선택 — 세 가지 기준과 흔한 실수]

자, 도구는 알았고, 이제 "어디에 측정점을 붙이느냐"가 문제입니다. 실제 프로젝트에 가보면 평가 대상이 될 수 있는 함수가 수십 개입니다. 그중에서 **첫 번째** 측정점을 잘못 고르면 1단계가 복잡해집니다. 세 가지 기준을 전부 만족하는 함수를 찾아야 합니다.

**기준 1: 입출력이 명확하다**

파라미터가 3개 이하고, 반환값이 단일 타입이면 이상적입니다. `question: str`을 받아서 답변 텍스트를 돌려주는 함수라면 완벽합니다. 반면에 파라미터가 `context, state, config, **kwargs`처럼 줄줄이 달려있고 반환값이 `Optional[Response]`인 함수는 일단 피하세요. 내부 상태를 여러 곳에서 읽고 쓰는 함수는 측정하기도 어렵고, 나중에 재현하기도 어렵습니다.

**기준 2: 성공 기준이 이미 있다**

기존 코드에 검증 로직이 있거나, "이 함수가 이것을 반환하면 성공"이라는 기준이 암묵적으로라도 존재하는 함수를 고르세요. 예를 들어 답변이 300단어 이상이어야 한다든가, 출처가 2개 이상이어야 한다든가 하는 기준이 코드 어딘가에 있다면, 그 기준이 `ground_truth`와 TCR 측정의 출발점이 됩니다. `ground_truth`를 따로 준비하지 않아도 일단 첫 숫자를 뽑을 수 있습니다.

**기준 3: 독립적으로 호출 가능하다**

다른 에이전트의 전역 상태에 의존하지 않고, 입력만 주면 단독으로 실행할 수 있어야 합니다. 재현 가능한 평가의 기초는 독립 호출 가능성입니다. 이 조건이 안 되는 함수에 측정을 붙이면, 나중에 동일한 테스트를 다시 실행했을 때 결과를 신뢰하기 어렵습니다.

그리고 흔한 선택 실수 두 가지도 짚어드릴게요.

첫째, **파이프라인의 중간 단계부터 시작하는 것**입니다. "이 내부 함수가 핵심이니까 여기부터 측정하자" 싶은 충동이 생기는데, 1단계에서는 외부 인터페이스, 즉 사용자가 직접 호출하는 최상위 함수부터 시작하세요. 중간 단계는 베이스라인이 생긴 다음에 파고드는 겁니다.

둘째, **`ground_truth`가 없으면 측정을 못 한다고 생각하는 것**입니다. `ground_truth`가 없어도 TCR, 응답 시간, 토큰 사용량, 응답 품질 점수는 전부 측정됩니다. 첫 단계에서 accuracy 숫자가 완벽할 필요는 없어요. 일단 파이프라인을 살아있게 만들고, 숫자부터 뽑는 것이 훨씬 중요합니다.

[PAUSE]

## [MAIN5] 범용 패턴: 레벨 0 래핑

[SLIDE: 레벨 0 래핑 — 기존 파일을 열지 않는다]

이제 코드로 넘어갑니다. 어떤 프로젝트든 기존 LLM 호출 함수를 감싸는 범용 레벨 0 래핑 패턴입니다.

[CODE: level0_pattern.py — QuickEval 세션 생성 + 기존 함수를 호출하는 래퍼 함수 작성 패턴]

패턴을 보시면 딱 세 가지 요소로 구성돼 있습니다.

첫째, `QuickEval("eval_results/")` 한 줄로 평가 세션을 시작합니다. 결과 파일이 저장될 경로를 인자로 넘겨줍니다. 폴더가 없어도 자동으로 만들어줍니다.

둘째, 기존 함수는 **전혀 건드리지 않습니다**. 소스 파일도 열지 않습니다.

셋째, 기존 함수를 호출하는 새로운 래퍼 함수를 작성합니다. `@eval_session.qa` 데코레이터를 붙이고, 함수 본문에서 기존 함수를 호출한 뒤 `str` 값만 반환합니다. 반환값이 `dict`나 객체라면 필요한 텍스트만 추출해서 반환하면 됩니다.

그 다음에는 기존 호출 코드에서 함수명만 바꾸면 됩니다. `existing_function(user_input)` 대신 `measured_function(user_input)`을 쓰는 거죠. 반환값은 완전히 동일합니다. 호출하는 쪽 코드는 아무것도 달라진 게 없어 보이지만, 내부적으로는 매 호출마다 결과가 기록되고 있는 겁니다.

이게 레벨 0의 전부입니다. 기존 코드 수정: 0줄. 새로 추가: 래퍼 함수 몇 줄. 이렇게 간단합니다.

## [MAIN6] Lecture_forge QAAgent 이식 — 6줄 추가로 측정 시작

[SLIDE: QAAgent 이식 — 세 가지 기준 적용 + 6줄 추가]

자, 이제 실제 프로젝트 코드로 들어갑니다. 예제 프로젝트 이름은 **Lecture_forge**입니다. 강의 자료를 자동으로 생성하는 AI 에이전트 시스템인데, 이 시리즈 전체를 통해서 계속 다루는 사례 프로젝트예요. 본인의 프로젝트 함수명으로 치환하면 그대로 쓸 수 있습니다.

세 가지 기준을 Lecture_forge에 적용하면 첫 번째 측정점으로 **`QAAgent.answer()`**가 선택됩니다. 왜 이 함수인지 이유를 보면요.

입출력이 명확합니다. `question: str`을 받아서 `{"answer": str, "sources": list, "confidence": float}` 딕셔너리를 반환합니다. 성공 기준도 코드에 명시돼 있습니다. 300단어 이상, 출처 2개 이상, 신뢰도 0에서 1 사이. 그리고 특정 `lecture_dir`만 있으면 단독으로 실행 가능합니다. 세 가지 기준 모두 충족합니다.

[CODE: ch24_quickeval_entry.py — cli/chat.py 수정 전/후 비교: QAAgent.answer()에 레벨 0 이식 6줄 추가]

코드 화면을 보시면서 설명드릴게요. 수정 전과 후를 비교하면, 추가된 코드가 딱 6줄입니다.

1번: `from agent_evaluator import QuickEval` 임포트 한 줄.
2번: `eval_session = QuickEval("lecture_eval_results/", auto_save=True)` 세션 생성 한 줄. `auto_save=True`를 쓴 이유는 잠시 후에 설명드릴게요.
3번: `_ctx = {}` 클로저 변수 선언 한 줄.
4번, 5번, 6번: `@eval_session.qa` 데코레이터가 붙은 `measured_answer` 래퍼 함수 세 줄.

여기서 반드시 짚고 넘어가야 할 부분이 있습니다. 왜 `result` 전체가 아니라 `result["answer"]`만 반환하냐는 거예요.

`@eval_session.qa` 데코레이터는 내부적으로 `@agent_eval(monitor, task_type="qa")`와 동일하게 동작합니다. 이 데코레이터는 함수의 **반환값을 `TaskResult.response` 필드 — 즉 `str` 타입**으로 캡처해서 정확도 점수를 계산합니다. Token F1, Jaccard, LCS 같은 지표들이 이 `response` 텍스트를 기준으로 계산되는 거죠.

만약 `result` 딕셔너리 전체를 반환하면 어떻게 될까요? `str({"answer": "서울입니다", "sources": [...], "confidence": 0.9})` 이렇게 딕셔너리를 문자열로 변환한 값이 `response`에 저장됩니다. 그 상태에서 accuracy scoring을 하면 모든 점수가 완전히 무의미해집니다. 딕셔너리 덤프 텍스트를 정답과 비교하는 셈이 되니까요.

그래서 평가에 쓸 텍스트인 `result["answer"]`만 반환하고, `sources` 같은 나머지 데이터는 `_ctx` 클로저 변수를 통해서 while 루프에 노출시킵니다. 기존 기능은 완전히 유지되고, 평가도 정확하게 됩니다.

이제 `auto_save=True` 이야기를 해볼게요. `while True` 루프는 종료되지 않기 때문에 루프 뒤에 `eval_session.save()`를 써봤자 절대 실행되지 않습니다. `auto_save=True`로 설정하면 10건마다 자동으로 결과 파일에 저장됩니다. 채팅 세션 중간에 프로세스가 갑자기 종료되더라도 결과가 보존됩니다. long-running 세션, 서버 프로세스, 배치 작업 등 언제 끝날지 모르는 실행에는 항상 `auto_save=True`를 쓰세요.

**결론**: 기존 `chat_command` 함수 로직 수정 0줄. 새로 추가한 코드 6줄. QAAgent에 대한 측정이 시작됩니다.

## [MAIN7] ContentWriter 이식 — 위임 어댑터 패턴

[SLIDE: ContentWriter 이식 — Delegation Adapter 패턴]

QAAgent는 `str`을 반환하니까 데코레이터를 바로 붙일 수 있었습니다. 그런데 현실에서는 이런 행운이 항상 따라오지 않습니다.

Lecture_forge의 **ContentWriter**가 바로 그 경우입니다. `write_section()` 메서드가 `SectionContent`라는 Pydantic 모델을 반환합니다. `@eval_session.qa` 데코레이터는 `str` 반환을 요구하기 때문에 직접 붙일 수 없습니다.

물론 `agent.py`를 열어서 레벨 1 방식으로 `return` 직전에 `monitor.record_task()`를 추가할 수도 있어요. 하지만 오늘은 더 강력한 패턴을 보여드릴 겁니다. **위임 어댑터(Delegation Adapter) 패턴**입니다. 기존 파일을 전혀 건드리지 않으면서도 모든 측정이 가능하고, 오류 케이스까지 빠짐없이 잡아냅니다.

아이디어는 이렇습니다. 기존 에이전트 인스턴스를 감싸는 어댑터 클래스를 **별도 파일**에 작성합니다. 어댑터가 원본 메서드를 호출하고, 결과를 `monitor`에 기록한 뒤, 원래 반환값을 **그대로** 돌려줍니다. 그리고 `__getattr__` 매직 메서드를 통해서 계측하지 않는 나머지 메서드와 속성들은 원본으로 **투명하게 위임**됩니다.

[CODE: ch24_quickeval_entry.py — eval/adapters.py: ContentWriterAdapter 클래스 — 위임 어댑터 패턴, try/finally 오류 기록 포함]

어댑터 구조를 보시면요.

생성자에서 기존 `ContentWriterAgent` 인스턴스, `PerformanceMonitor` 인스턴스, 그리고 학습 목표 리스트를 받습니다.

`write_section()` 메서드는 `try/finally` 구조로 구성됩니다. `try` 블록에서 원본 `self._agent.write_section()`을 호출하고, `finally` 블록에서 `create_taskresult()`로 결과를 기록합니다. 여기서 핵심은 `finally` 블록입니다. 예외가 발생하더라도 `finally`는 반드시 실행되기 때문에, `write_section()`이 에러를 던지는 경우도 `has_error=True`인 TaskResult로 기록됩니다. 이게 Gate C의 FaultTolerance 측정에 자동으로 포함됩니다.

`create_taskresult()`를 호출할 때 `extra` 딕셔너리에 `phase`, `section_id`, `word_count` 같은 부가 정보를 넣습니다. Gate G의 단계별 지연 분석에 활용할 수 있는 데이터입니다. 지금은 "그냥 넣어둔다"는 것만 기억하세요. 나중에 이 데이터가 어디서 빛나는지는 Ch26에서 다룹니다.

마지막 `__getattr__`은 한 줄짜리입니다. `return getattr(self._agent, name)`. 이 한 줄이 어댑터의 "투명성"을 만들어냅니다. `write_section()` 외의 다른 메서드나 속성에 접근하면 자동으로 원본 에이전트에 위임됩니다. 어댑터를 쓰는 코드 입장에서는 기존 `ContentWriterAgent`를 쓰는 것과 완전히 동일하게 느껴집니다.

[CODE: ch24_quickeval_entry.py — cli/commands/create.py: generate_lecture() 안에서 ContentWriterAdapter 적용 — 2줄 추가]

진입점 코드는 더 간단합니다. 기존에 `writer = ContentWriterAgent(vector_store=vs)`로 생성하던 코드 바로 아래에, `if _eval_monitor:` 조건으로 어댑터로 교체합니다. 두 줄이에요. 모니터가 없는 경우엔 기존 에이전트가 그대로 동작합니다. 완전한 opt-in 설계가 됩니다.

이 패턴의 장점을 정리해볼게요.

첫째, `ContentWriterAgent`의 소스 파일을 열지 않습니다. 원본 코드는 손도 대지 않습니다.
둘째, 어댑터를 씌운 후에도 `writer.write_section()`의 인터페이스와 반환값은 완전히 동일합니다.
셋째, 모니터가 없는 환경에서도 자연스럽게 우회됩니다.
넷째, `try/finally` 덕분에 오류 케이스도 빠짐없이 기록됩니다.

이 패턴을 보고 "내 프로젝트에도 바로 쓸 수 있겠다" 싶으신 분들이 분명 있을 겁니다. 맞습니다. 클래스 기반 에이전트라면 거의 모든 경우에 이 패턴이 작동합니다. 어댑터 클래스명과 감쌀 메서드명만 바꾸면 됩니다.

**결론**: `content_writer/agent.py` 수정 0줄. 새 파일 `eval/adapters.py` 작성. `create.py`에 2줄 추가.

## [MAIN8] 첫 실행 — 어떤 숫자가 보이는가

[SLIDE: 첫 번째 측정 결과 — 숫자들이 말해주는 것]

두 개의 측정점을 삽입했습니다. 이제 Lecture_forge를 실제로 돌려볼 차례입니다.

[CODE: ch24_quickeval_entry.py — CLI 실행 명령 + lecture_eval_results/ 폴더에 JSON·HTML 파일 생성 확인]

실행하고 나면 `lecture_eval_results/` 폴더에 JSON 파일과 HTML 파일이 생성됩니다. 이 두 파일이 보이면 1단계 이식에 성공한 겁니다. 축하드립니다.

그럼 이 첫 번째 결과에서 어떤 숫자들이 보이는지 살펴볼게요.

**TCR, Task Completion Rate**. 가장 먼저 봐야 할 숫자입니다. 예외 없이 완료된 태스크의 비율이에요. QA 세션에서 10번 질문했는데 한 번도 에러가 없었다면 100%입니다. 만약 100% 미만이라면, 에러가 발생한 케이스가 있다는 뜻이고, JSON 파일에서 바로 어느 질문에서 오류가 났는지 추적할 수 있습니다.

**평균 응답 시간**. 질문당 LLM 호출이 얼마나 걸렸는지 밀리초 단위로 나옵니다. 처음 봤을 때 "이렇게 느렸어?" 하고 놀라는 경우가 많습니다. 평소에 "빠르다"고 체감하던 응답이, 실제로 측정해보니 P95가 8초였던 사례도 있습니다. 느낌과 측정값이 다른 경우가 생각보다 훨씬 많습니다.

**accuracy 점수**. `ground_truth`를 제공한 케이스에서는 Token F1, Jaccard, LCS 기반 정확도가 계산됩니다. `ground_truth` 없이 실행한 케이스는 0으로 표시되는데, 이건 나쁜 결과가 아닙니다. "아직 측정 안 함"을 의미합니다. 이후에 골든 데이터셋을 만들면서 채워나가는 거예요.

**토큰 사용량**. 질문당 평균 몇 토큰을 쓰는지, 총 비용이 얼마나 됐는지 보입니다. "이 에이전트를 한 달에 100만 번 호출하면 비용이 얼마지?"라는 질문을 처음으로 근거 있게 할 수 있게 됩니다.

ContentWriter 결과에는 `extra` 딕셔너리에 넣었던 `word_count`와 `section_id`도 함께 기록돼 있습니다. 나중에 "어떤 섹션이 단어 수가 부족했는가"를 분석할 때 이 데이터가 유용해집니다.

## [MAIN9] 베이스라인 설정 — 첫 숫자 이후 할 일

[SLIDE: 베이스라인 — 판단이 아니라 기준점 설정]

첫 번째 숫자를 얻었습니다. 여기서 한 가지 꼭 기억해야 할 게 있습니다.

**첫 번째 측정값은 "좋다/나쁘다"를 판단하는 게 목적이 아닙니다. 베이스라인을 설정하는 것이 목적입니다.**

지금 이 숫자가 앞으로 모든 개선의 기준점이 됩니다. 첫 번째 TCR이 70%라고 실망할 필요 없어요. "지금 30%가 에러로 죽는구나. 다음에 85%로 올리면 15%포인트 개선이다"라고 생각하면 됩니다.

응답 시간이 P95 기준 8초라고 패닉할 필요 없습니다. "P95를 3초 이하로 낮추겠다"는 목표를 설정하는 출발점이 된 겁니다.

1단계가 끝난 후 취해야 할 액션은 딱 세 가지입니다.

**첫째, 숫자를 팀과 공유하세요.** HTML 리포트 파일을 팀 슬랙에 올리세요. "우리 에이전트 현재 상태가 이렇습니다"를 데이터로 보여주는 첫 순간입니다. 팀원들의 반응이 달라집니다.

**둘째, 이상치를 찾으세요.** TCR이 낮은 태스크, 응답 시간이 유독 긴 케이스를 확인하세요. JSON 파일에 태스크별 결과가 다 들어있어서 필터링이 쉽습니다.

**셋째, ground_truth 10개를 만드세요.** QAAgent의 대표적인 질문 10개에 대해 기대하는 답변을 작성합니다. 다음 실행에서 accuracy 숫자가 의미 있게 채워지기 시작할 겁니다.

레벨 0 이식을 마치고 나면 여러분 앞에 대시보드가 열립니다. 이 대시보드를 보는 순간부터 에이전트를 "느낌으로" 평가하는 시대가 끝나고, 숫자로 대화하는 시대가 시작됩니다.

## [MAIN10] 자주 막히는 지점과 함정 피하기

[SLIDE: QnA — 이식 중 자주 막히는 순간들]

실제로 이 패턴을 적용해보신 분들이 자주 막히는 지점들을 짚어드릴게요.

**Q: 비동기 에이전트, 즉 `async def`에는 어떻게 적용하나요?**

`@eval_session.qa`는 동기 함수용입니다. `async def`로 선언된 함수에는 `async_evaluation_session` 컨텍스트 매니저를 사용하거나, `create_taskresult()`를 직접 호출하는 방식이 더 안전합니다. `async with async_evaluation_session("파일명") as monitor:` 블록 안에서 `await`로 에이전트를 호출하고, `monitor.record_task()`로 수동 기록하는 패턴이 깔끔합니다.

**Q: 같은 함수가 여러 스레드에서 동시에 호출되면 데이터가 뒤섞이지 않나요?**

`QuickEval`과 `PerformanceMonitor` 내부는 `threading.Lock`으로 보호되어 있습니다. 동시 호출에서도 결과 누락이나 중복 기록이 발생하지 않습니다. 멀티스레드 환경에서도 안심하고 쓰셔도 됩니다.

**Q: `ground_truth` 없이 실행하면 accuracy가 0으로 나오는데, 이 상태로 진행해도 의미가 있나요?**

충분히 의미 있습니다. 1단계에서는 TCR, 응답 시간, 토큰 사용량만으로도 유용한 인사이트가 충분히 나옵니다. `ground_truth`는 2단계에서 골든 데이터셋을 만들면서 추가하면 됩니다. 지금은 파이프라인을 살아있게 만드는 것이 accuracy 숫자를 채우는 것보다 훨씬 중요합니다.

**Q: ContentWriter 어댑터에서 `__getattr__`이 무한 재귀에 빠지는 경우는 없나요?**

`__getattr__`은 파이썬이 일반적인 속성 조회 방식으로 속성을 찾지 못할 때만 호출됩니다. `self._agent`는 `__init__`에서 직접 `self.__dict__`에 저장되기 때문에 `__getattr__`이 `_agent`를 찾으려 할 때 재귀가 발생하지 않습니다. 안전합니다.

**Q: QAAgent와 ContentWriter를 동시에 측정하면 결과가 섞이지 않나요?**

`PerformanceMonitor` 인스턴스 하나를 여러 어댑터가 공유해도 됩니다. `monitor.record_task()`는 thread-safe합니다. 단, `task_id`가 겹치지 않도록 주의하세요. 각 어댑터마다 `qa_001`, `section_001` 같이 prefix를 붙이는 것이 좋습니다. 결과 파일에서 `task_type`으로도 필터링할 수 있어서 구분이 됩니다.
